# Architecture Decision Records

## 철학
학습이 최우선이다. 처음부터 완성형을 넣지 않고, 문제를 먼저 겪어 보고, 수치로 남긴 다음, 다음 기법을 도입한다. 오버엔지니어링을 하지 않는다. 어필 문구에는 직접 측정한 수치나 코드 근거가 있는 것만 남긴다. 결정은 단계를 시작할 때 grilling으로 정하고 이 문서에 기록한다.

> 상태 표기: **확정** / **잠정**(바뀔 수 있음) / **미결**(정할 시점이 정해져 있음)

### ADR-001: C++17 + Boost.Asio 서버, Unity 클라이언트
**상태**: 확정
**결정**: 서버는 C++17 + Boost.Asio(이 저장소), 클라는 Unity(`~/Workspace/Unity_Projects/T1`). proto 원본은 Unity 쪽 `Common/Protocol`에 있다.
**이유**: 예전 C# 서버(리니지라이크)를 넘어, 저수준 네트워크와 동시성을 직접 다뤄 보며 배운다.
**트레이드오프**: 서버와 클라 언어가 달라서 결정론 시뮬레이션은 사실상 불가능하다(ADR-011). proto ID를 양쪽에서 맞춰야 한다(R3 전까지 수동).

### ADR-002: 존 로직은 공용 game 풀 + 존별 JobSerializer, 세션 I/O는 strand 후보
**상태**: 확정 (세션 I/O 쪽은 ADR-008에서 확정)
**결정**: 공용 game io_context 풀 위에서 존마다 JobSerializer 하나로 직렬화한다(동적 스케줄링). 액터 모델은 쓰지 않는다. 세션 I/O처럼 핸들러가 작고 순서만 보장하면 되는 곳에는 strand를 쓴다.
**이유**:
- strand도 핸들러를 하나씩 처리하지 않는다. 실제 동작(`strand_executor_service`): ① post가 오면 mutex를 잡고, 이미 실행 중이면 `waiting_queue`에 넣고, 아니면 invoker를 1개만 io_context에 post한다. ② invoker는 ready queue를 락 없이 루프로 전부 실행한다. ③ 다 끝나면 waiting queue를 O(1)로 통째로 옮기고(splice), 남은 게 있으면 자기 자신을 다시 post한다. 이 재post가 다른 strand에게 양보하는 지점이다. 그래서 워커를 깨우는 비용은 배치당 1번, 핸들러당 비용은 mutex 1번 + push 1번이다. 지금의 JobSerializer도 같은 구조다(`_isExecuting`이 strand의 `locked_`에 해당).
- **진짜 차이는 시간 예산이다.** strand는 쌓인 만큼 개수·시간 제한 없이 돈다. 존 로직은 잡이 크고 틱 데드라인과 엮여 있어서 시간 예산이 필요하다.
- 스레드 배정: 존 하나당 스레드 하나(1:1)는 확장되지 않고, 스레드 N개가 존 M개를 나눠 맡는 정적 배정(M:N)은 부하 불균형에 약하다(마을·보스 존에 사람이 몰리면 그 스레드만 터진다). 고정 틱과 스레드 고정은 무관하다. 동적 풀 위에서도 존마다 tick 잡을 데드라인에 맞춰 post하면 된다.
- 캐시 친화성은 "한 존의 틱이 한 코어에서 끊기지 않고 실행된다"(틱 내부 지역성)까지만 주장할 수 있다.
**트레이드오프**: 처리량만 보면 strand가 이길 수도 있다. strand는 핸들러 메모리를 재활용하지만 JobSerializer는 `make_shared<Job>`과 `std::function` 할당이 생긴다. 1-10 JobBench로 측정한다.

### ADR-003: 20Hz 고정 틱, 절대 데드라인, 늦으면 건너뛰기
**상태**: 확정. 단, 20Hz가 맞는지는 원래 순서대로 1-7을 이 값으로 구현한 뒤 M0-c(틱 간격별 반응 차이)와 1-11(틱 비용) 측정 결과를 보고 다시 검토한다(2026-10-19)
**결정**: 20Hz, 고정 dt 50ms. 존이 생성되면 바로 틱을 돌린다. 다음 틱은 절대 데드라인(`start + k·50ms`)으로 예약하고 `steady_timer::expires_at`을 재사용한다. 데드라인을 넘기면 따라잡지 않고 건너뛴 뒤 횟수만 센다.
**이유**: 키보드 이동은 위치가 시간의 함수라서 시간을 적분할 주체(틱)가 필요하다. 클릭 셀 이동은 "한 칸 이동"이라는 이산 이벤트라 이벤트 구동으로 충분했지만 여기서는 아니다. 몬스터 AI, 판정 윈도우, 버프, AOI도 이동 방식과 상관없이 시간 기반이라 존 틱은 어떤 경우에도 필요하다. 상대 시간으로 예약하면 오차가 누적된다.
**트레이드오프**: 건너뛴 틱만큼 시뮬레이션이 느려진다(몰아서 실행하면 순간 부하가 더 커지므로 이쪽을 택했다).

### ADR-004: JobSerializer 시간 예산 5ms에서 시작
**상태**: 잠정 (1-11에서 확정). 예산은 틱 간격에 맞춰 정하는 값이라 1-11에서 ADR-003의 틱 간격 재검토와 함께 정한다. 그때까지 코드 값은 기존 64ms로 둔다(1-6은 잡 단위 확인 구조만 바꿨다)
**결정**: 5ms로 시작하고, 1/5/10/64ms에서 "다른 존의 틱 데드라인 초과율"을 측정해 확정한다. `DRAIN_COUNT(100)`은 "락을 한 번 잡을 때 꺼내는 개수"를 뜻한다. 예산은 잡 단위로 확인한다(1-6).
**이유**: 한 존이 워커를 오래 붙잡으면 같은 풀의 다른 존 틱이 밀린다.
**트레이드오프**: 예산이 작을수록 재post(양보)가 잦아져 처리량이 떨어진다.

### ADR-005: 존 큐는 mutex 유지 (락프리 안 함)
**상태**: 확정
**결정**: mutex를 유지한다. 수정할 것: ① 시간 예산을 잡 단위로 확인 ② 배치 vector 재사용 ③ 잡당 할당 비용은 벤치 결과를 보고 결정.
**이유**:
- 존의 `_jobs` 큐는 **MPSC**(Multi-Producer, Single-Consumer: 여러 스레드가 넣고 한 번에 한 스레드만 꺼냄) 모양이다.
- **Vyukov MPSC**(wait-free, intrusive)의 push는 `head.exchange` 1번 + `prev->next` 저장으로 끝난다. 함정이 있다. 두 연산 사이의 짧은 순간에는 꺼내는 쪽에서 큐가 "비어 보인다". 그래서 생산자가 push를 끝낸 **뒤에** 실행 플래그를 확인해야 lost wakeup이 생기지 않는다.
- 지금은 mutex 안에서 큐와 플래그를 함께 다루므로 lost wakeup이 원천적으로 생기지 않는다. 존당 push는 초당 약 4,000번(200명 × 20Hz) 수준이라 mutex로 충분하다고 판단했다. 이것도 측정으로 확인한다.
**트레이드오프**: 극단적인 경합에서는 락프리보다 느릴 수 있다. 측정으로 병목이 확인되기 전까지는 감수한다.

### ADR-006: 게임 타이머는 "N틱 후" + 존별 min-heap
**상태**: 확정 (구현은 R6)
**결정**: "N틱 후" 형태로 표현하고, 존마다 min-heap 하나에 넣는다. 구현은 처음 필요해지는 몬스터 단계에서 한다.
**이유**: 틱 단위로 표현하면 존 틱과 같은 시간축에서 결정적으로 처리된다. 지금의 `PostAfter`(실시간 기반)는 틱과 어긋난다.
**트레이드오프**: 틱보다 세밀한 타이밍은 표현할 수 없다(50ms 단위).

### ADR-007: 전송 계층은 TCP
**상태**: 확정
**결정**: TCP를 유지한다.
**이유**: MMO 메시지는 대부분 반드시 도착해야 한다(아이템, 데미지, 스킬 사용, spawn/despawn). AOI는 변화분만 보내므로 despawn 하나를 잃으면 유령이 남는다. ADR-013(b) 의사 변경 이벤트도 TCP의 신뢰성을 전제로 한다. PvE라 지연 허용 폭이 넓다(목표: 지연 100±20ms). UDP로 가면 재전송·순서 보장을 직접 만들어야 한다.
**트레이드오프**:
- head-of-line blocking: 패킷 하나가 유실되면 재전송될 때까지 뒤 데이터 전부가 대기한다. 원격 보간 버퍼(100ms)가 바닥날 수 있다. M2-b(버퍼 고갈 빈도)에서 측정한다.
- Nagle 알고리즘: 작은 패킷을 붙잡아 delayed ACK와 겹치면 수십 ms 지연이 낄 수 있다. 지금은 서버·클라 모두 `TCP_NODELAY`를 설정하지 않았다. M1-c에서 켬/끔을 비교 측정한다.

### ADR-008: 세션 close 경쟁 해결 방식
**상태**: 확정 (2026-10-20, 1-4 시작 시 grilling)
**결정**: (a) 세션 strand.
- 소켓을 세션마다 `make_strand(network io_context)`로 만든 strand를 executor로 삼아 만든다. 핸들러에 executor를 따로 붙이지 않으면 asio는 소켓의 executor에서 완료 핸들러를 실행하므로, 읽기·쓰기 완료 핸들러(`async_write` 안쪽의 후속 `async_write_some` 포함)가 전부 strand에서 돈다.
- 소켓과 쓰기 상태(`_writeQueue`, `_inflightBuffer`)는 strand 위에서만 만진다. strand는 완료 핸들러의 실행 위치만 정하고, `async_*` 시작은 부른 스레드에서 일어나므로 strand 밖 진입점은 post로 넘긴다.
  - `Connect`: 본문을 post한다(서버의 accept 핸들러는 acceptor의 executor에서 돈다).
  - `Send`: push는 지금처럼 mutex 큐에 하고, `_isWriting`을 처음 세운 쪽만 `Write`를 post한다(쓰기 배치당 post 1번). `_isWriting`의 의미는 "쓰기 중"에서 "쓰기가 예약됐거나 진행 중"으로 바뀐다.
  - `Disconnect`: `_isConnected.exchange`는 부른 자리에서 하고, close·`RemoveSession`·`OnDisconnected`는 strand에서 한다.
- 전부 dispatch가 아니라 post로 넘긴다. dispatch는 이미 strand 위면 그 자리에서 실행되어, 패킷 핸들러 안에서 끊으면 파싱 도중에 close와 `OnDisconnected`가 끼어든다.

**이유**:
- 소켓의 소유자를 하나로 만든다. "존 상태는 그 존의 JobSerializer만 만진다"와 같은 원칙이다.
- (b)는 `shutdown`도 다른 스레드의 쓰기 시작과 겹친다. 지금 asio 구현에서 shutdown은 fd 시스템 콜만 해서 실제로는 문제가 없지만, asio 문서상 같은 소켓 객체를 여러 스레드가 동시에 쓰는 것은 unsafe라 안전 근거가 구현 세부가 된다. 참조가 새면 fd도 샌다.
- mutex로 소켓 조작을 감싸는 방법은 막지 못한다. `async_write`는 composed operation이라 두 번째 이후 `async_write_some`은 asio가 완료 쪽(network 스레드)에서 부르고, speculative write 때문에 mutex를 쥔 채 `sendmsg`를 하게 된다.
- 읽기도 같은 strand에 둔다. close가 strand 위에 있으면 읽기 시작(`Recv()`)도 strand 위여야 겹치지 않는다. 바이트 순서는 strand가 아니라 "읽기는 한 번에 하나만 건다"는 규칙이 보장한다.
- 부수 효과: 패킷 핸들러(`OnRead`)와 `OnDisconnected`가 같은 strand에서 돌아 둘 사이의 `GameSession` 필드 경쟁이 사라진다. game 스레드에서 읽는 곳(`World.cpp:136`의 `GetSelectedPlayer()`)은 1-5에 남는다.

**트레이드오프**:
- 쓰기 배치당 post 1번(network 스레드 깨우기)이 는다. 대신 `sendmsg`가 game 스레드에서 network 스레드로 옮겨 간다(봇 100 기준 `World::Tick` 샘플의 54%). 틱이 줄어드는지는 가설이고, 1-4 전후로 잰다.
- 같은 세션의 읽기·쓰기 핸들러가 동시에 돌지 않아서, 쓰기가 읽기 핸들러 뒤에 줄을 설 수 있다. strand 위 핸들러는 짧아야 한다(파싱과 post만. DB 동기 호출 금지, R9). 대기시간은 strand 대기 지표로 잰다.
- strand가 모아 보내기를 만들지는 않는다. post와 `Write` 실행 사이에 우연히 쌓이는 만큼만 묶인다. 의도적으로 모으는 방법(틱 끝 flush)은 1-4 측정 뒤 따로 정한다.

### ADR-009: 핫 존은 인원 상한 + 채널
**상태**: 확정
**결정**: 존당 200명 상한 + 채널로 대응한다. 병목이 측정되면 송신 단계를 병렬화한다. 액터별 1회 직렬화는 이미 구현돼 있다(`World.cpp:91-93`).
**이유**: 사람이 아주 많을 때의 진짜 병목은 스레드 배정이 아니라 **보는 사람 수 × 보이는 대상 수만큼 늘어나는 송신(팬아웃)**이다.
**트레이드오프**: 같은 존이라도 채널이 다르면 서로 못 본다.

### ADR-010: 2.5D 좌표
**상태**: 확정
**결정**: 서버 축은 (x, y)가 바닥 평면, z가 높이다. 클라의 축 변환은 한 곳에 모은다.
**이유**: 이동은 평면에서, 판정은 높이 범위를 포함해서 한다(점프·띄우기로 z축 회피, R7).
**트레이드오프**: Unity(y-up)와 축이 달라서 변환 지점이 흩어지면 버그가 난다. 그래서 한 곳에 모은다(M2-a).

### ADR-011: 서버 권위 + 상태 복제 (결정론 lockstep 아님)
**상태**: 확정
**결정**: 서버가 시뮬레이션하고 결과(위치)를 보낸다. 클라 예측은 근사치로 충분하고, 어긋난 만큼은 reconciliation이 보정한다. 이동은 0~5단계로 나눠 진행한다(R2).
**이유**: 결정론 lockstep은 입력만 주고받고 모든 참가자가 비트 단위까지 똑같이 계산하는 방식(RTS, 격투게임 롤백)이다. C++ 서버와 C# 클라 조합에서는 사실상 불가능하다. 참고로 언리얼이 MMO에 안 맞는 이유는 틱 때문이 아니다. 프로세스 하나가 월드 하나, 게임 스레드 하나로 돌고, 복제 비용이 접속자 × 액터로 커지고, 존 분산과 영속화 기능이 없어서다.
**트레이드오프**: 대역폭이 입력 전송보다 크다. 예측 오차 보정이 필요하다.

### ADR-012: 보정·보간 수치
**상태**: 잠정 (R2에서 측정 후 조정)
**결정**: 내 캐릭터는 오차가 0.5 미만이면 약 100ms에 걸쳐 흡수하고, 그 이상이면 바로 맞춘다. 원격 캐릭터는 2틱(100ms) 지연 보간, 외삽은 최대 1틱까지만 하고 그 뒤에는 멈춘다.
**이유**: 작은 오차를 순간이동으로 고치면 떨림이 보이고, 큰 오차를 천천히 고치면 벽 통과처럼 보인다. 지연 보간은 스냅샷 2개 사이를 보간할 여유를 만든다.
**트레이드오프**: 원격 캐릭터가 항상 100ms 과거에 있다.

### ADR-013: 이동 입력 프로토콜
**상태**: 미결 (R2 4단계에서 측정값으로 결정)
**결정**: 다음 둘 중 하나. (a) 고정 주기 입력 스트림: 클라도 50ms 고정 스텝으로 돌고, 스텝마다 `{seq, dir}`을 보낸다. 서버는 틱당 1개씩 소비한다(입력 버퍼). (b) 의사 변경 이벤트: 입력이 바뀔 때만 `{seq, dir}`을 보낸다. TCP라서 주기적인 재전송은 필요 없다.

### ADR-014: AOI는 셀 인덱스 + 원형 반경 + 히스테리시스
**상태**: 잠정 (세부는 R4)
**결정**: 셀은 후보를 고르는 공간 인덱스로만 쓰고, 가시성은 원형 반경 + 히스테리시스로 판정한다. 들어올 때는 R, 나갈 때는 R + margin.
**이유**: 경계에서 enter/leave가 반복되는 원인은 float가 아니라 경계 근처에서 왕복하는 이동이다. 그래서 히스테리시스는 셀이 아니라 **가시 반경**에 건다. margin 후보 식: `margin ≥ 2 × v_max × T`(T = 가시성 재계산 주기). 이렇게 잡으면 재계산 사이에 R 안쪽에서 갑자기 나타나는 일이 없다. R의 출발점: 직교 카메라 size 10, 60° 기울기, 16:9 화면이면 화면 구석까지의 지면 거리가 약 21이라 R은 22~25.
**트레이드오프**: 반경 밖 margin 구간의 대상에게도 송신이 계속돼 대역폭이 조금 늘어난다.

### ADR-015: 길찾기·충돌은 NavMesh 대신 타일 그리드, 셀 1.0
**상태**: 확정 (셀 크기와 벽 부풀리기는 T-3에서 재검토)
**결정**: 타일 그리드를 쓴다. 이동 0~2단계는 셀 크기 1.0. 오브젝트 충돌은 그리드 셀에 반영하고, 액터끼리의 충돌은 원형 검사로 따로 처리한다.
**이유**: 서버에서 NavMesh(Recast/Detour)를 쓰는 것 자체는 가능하다. 그래도 그리드를 택한 이유는 ① 2.5D 평평한 지형이라 경사·다층·다리를 쓸 일이 없고 ② 그리드 하나를 충돌, A*, LOS, AOI가 함께 쓰고 ③ 동적 장애물은 셀 값만 바꾸면 되고 ④ A*와 LOS를 직접 구현하면서 배우기 때문이다.
**트레이드오프**: 계단 모양 경로 → LOS 스무딩. 벽 정밀도가 셀 크기에 묶임 → 셀 크기 조정(예: 0.5). 큰 몬스터의 통과 폭 → clearance 처리(R6).

### ADR-016: 검증 방식은 로직 종류별로 나눈다
**상태**: 확정 (2026-10-18 개정: TDD 일괄 적용 → 종류별 검증. 도구는 1-1에서 구축 완료)
**결정**:

| 종류 | 검증 방식 | 예 |
|---|---|---|
| 규칙 로직 (명세가 먼저 정해짐) | **TDD**. 테스트를 먼저 쓰고 통과하는 구현을 쓴다(GoogleTest) | 프레이밍, 핸들러 방어, 시간 예산, 고정 틱, 셀 변환, 이동 입력 검증, A*/LOS, AOI 변화분, 판정 도형, 데미지·쿨다운, 인벤토리 |
| 감각·튜닝 로직 (플레이해 봐야 정해짐) | 플레이와 측정으로 값을 정한 **뒤**, 깨지면 안 되는 **불변식만** 회귀 테스트로 굳힌다. 튜닝 값 자체는 assert하지 않는다 | 이동 속도, 보정·보간 수치, AI 행동, 보스 패턴, 텔레그래프·관대화 수치 |
| 동시성·네트워크 | 봇 시나리오 + TSan + 지표 | 세션 close 경쟁, 게임 상태 데이터 레이스 |
| 일부러 겪어 보는 실험 | `docs/measurements.md` 기록 | 틱 주기 비교, 지연·Nagle 측정, 버퍼 고갈 빈도, JobBench |

도구: GoogleTest(FetchContent, v1.17.0), 루트 CMake의 `T1_SANITIZE` 캐시 변수(`-DT1_SANITIZE=thread`).
**이유**:
- TDD는 명세가 먼저 정해지는 규칙 로직에서 이득이 크다. PRD의 "반복하지 말 참조 버그"(데미지 이중 차감, MP를 MaxHp로 clamp 등)를 막는 것도 이런 테스트다.
- 플레이해 봐야 정해지는 값에 테스트를 먼저 쓰면 임의의 숫자를 박제하게 된다. 튜닝할 때마다 깨지기만 하고 아무것도 지켜 주지 않는 테스트(change detector)가 남는다. 그래서 "속도는 5.0이다" 대신 "속도는 상한을 넘지 않는다", "벽 셀에 들어가지 않는다", "추적 중 일정 거리를 벗어나면 Return으로 간다"처럼 튜닝과 무관하게 항상 참인 불변식만 테스트한다.
- AI·보스의 "자연스러움" 같은 창발적 행동은 assert로 표현되지 않는다.
- 소켓·스레드가 얽힌 버그는 단위 테스트로 재현하기 어렵고, 데이터 레이스는 TSan이 가장 확실하게 잡는다.
- 고정 dt 틱(ADR-003) 덕분에 게임 로직을 `다음 상태 = step(현재 상태, 입력, dt)` 순수 함수로 떼어 내기 쉬워, 불변식 테스트를 쓰기 좋다.
**트레이드오프**: 감각·튜닝 로직은 테스트 커버리지가 낮아서, 회귀는 불변식 테스트와 플레이로만 잡힌다. TSan 빌드는 느리다(별도 빌드 디렉터리 `build/tsan`). 첫 configure 때 GitHub에서 googletest를 내려받는다.

### ADR-021: 세션 상태는 세션 strand, 존 상태는 존 큐가 소유한다
**상태**: 확정 (2026-10-21~22, 1-5)
**결정**:
- "플레이어를 어느 World로 보냈나"를 `GameSession::_enteredWorld`(세션 메모)에 적는다. 세션 strand가 입장 쪽지를 보내는 순간 적고, 이동·나가기·끊기는 그 값을 보고 같은 World 큐에 바로 Post한다. 나가기와 끊기에서 비운다.
- `GameSession` 멤버는 세션 strand만, `Actor` 멤버(`_world` 포함)는 그 존의 JobSerializer만 읽고 쓴다. World 잡은 세션 필드를 읽지 않고 인자로 받은 값을 쓴다.
- strand 위에서는 O(1) 판단과 Post만 한다. 명단을 보거나 플레이어 수만큼 도는 일은 World 큐에서 한다.
- 월드 목록(`GameLoop::_worlds`)은 접속을 받기 전(스레드 시작 전)에 채우고 그 뒤로 바꾸지 않는다. strand는 락 없이 `FindWorld`로 읽는다.
- 상태 규칙은 strand가 판단하고, 상태에 맞지 않는 패킷은 위반으로 끊는다. 상태는 기존 필드로 구분한다(`_players`가 비었나, `_enteredWorld`가 있나).

| 패킷 | 허용 상태 | 처리 후 |
|---|---|---|
| `C_FindMyPlayers` | 목록 없음 | 목록 받음 |
| `C_EnterWorld`(올바른 index) | 목록 받음 | 월드 안 |
| `C_Move` | 월드 안 | 월드 안 |
| `C_LeaveWorld` | 월드 안 | 목록 받음 |

- 끊기로 한 세션(`IsConnected() == false`)의 패킷은 `OnRead`에서 처리하지 않는다. `Disconnect()`는 플래그만 바로 내리고 정리(`OnDisconnected`)는 strand에 post하므로, 그 뒤에 도착한 읽기 결과가 `OnDisconnected` 다음에 처리되면 퇴장을 보낼 곳이 없는 입장이 생긴다(코드 추론, 실행에서 관찰되지는 않았다).

**이유**:
- 퇴장을 보낼지 정하려면 "입장을 보냈나"를 알아야 하는데, 예전에는 "World가 입장을 끝냈나"(`Actor::_world`, World 큐가 적는 값)를 strand가 읽었다. 입장은 strand → GameLoop 큐 → World 큐로 두 번 갈아타고 퇴장은 World 큐로 바로 가서, 입장 중에 끊기면 null World로 크래시가 나거나 퇴장을 보내지 않아 유령이 생길 수 있었다. 다른 스레드가 쓰는 값을 읽어 TSan 경고도 났다(measurements 1-5).
- 메모는 보내는 순간 적으므로 늦지 않고, 같은 strand가 같은 World 큐에 넣으므로 입장 → 퇴장 순서가 보장된다.
- 검토한 대안: 모든 쪽지를 GameLoop 큐를 거쳐 World로 보낸다. 같은 FIFO 경로라 순서는 보장되지만, 모든 이동 패킷이 큐 하나를 지나서 존이 늘면 병목 후보가 되고 이동이 2홉이 된다.
- `Actor::_world`를 strand 소유로 바꾸지 않았다. Player의 나머지 상태(위치, `MoveInfo`)는 World 큐 소유라 필드마다 주인이 달라지고, 몬스터도 Actor인데 세션이 없다.
- 상태 판단을 strand에 둔 이유: strand는 클라가 보낸 순서 그대로 패킷을 본다. 1-3에서 "정상 클라도 타이밍상 보낼 수 있다"며 무시한 것은 World가 늦게 적는 값을 봤기 때문이고, 메모를 보면 그런 타이밍이 없다. 정상 클라는 접속당 `C_FindMyPlayers` 1번 → `C_EnterWorld` 1번 → `C_Move` 반복이고 `C_LeaveWorld`는 보내지 않는다.

**트레이드오프**:
- 메모는 "보낸 곳"이지 "실제로 있는 곳"이 아니다. 진짜 명단은 `World::_players`다. World가 입장을 거절해도 메모는 남지만, 퇴장은 명단에서 못 찾고 끝나 안전하다. 존 이동(R5)이 생기면 World 잡이 대상이 자기 명단에 있는지 먼저 확인해야 한다(`HandleMove_Internal`은 지금 확인하지 않는다).
- 서버가 도는 중에 월드를 만들거나 지울 수 없다. `CreateWorld`/`RemoveWorld`는 스레드 시작 전에만 부른다. 채널·인스턴스(R5)에서 다시 정한다.
- 서버가 먼저 플레이어를 월드에서 빼는 경로(강제 퇴장, 존 이동)가 생기면 클라가 이미 보낸 패킷이 위반으로 끊길 수 있다. R5의 "이동 중에 도착한 패킷" 결정에 넣는다.
- `C_FindMyPlayers`는 접속당 1번만 허용한다. 로비로 돌아가는 기능(R9)이 생기면 다시 정한다.
- World 람다의 raw `this` 캡처는 월드가 서버 종료까지 살아 있어 잠재 문제로 남긴다(R5에서 월드를 지울 때 처리).

**검증**: `tests/SessionStateTest.cpp`(상태 규칙), `scripts/churntest.sh`(measurements 1-5)
