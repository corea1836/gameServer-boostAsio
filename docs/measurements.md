# 측정 기록

어필·성능 주장은 이 문서의 수치만 근거로 쓴다(ADR-020). 측정마다 환경과 재현 방법을 같이 남긴다.

## 1-11 AOI 이전 기준선 (2026-10-20, 1차)

**환경**
- Apple M4 Pro(P코어 10 + E코어 4), macOS 15.3.1, Release 빌드
- 서버와 봇이 같은 머신에서 돈다(봇 CPU가 서버와 코어를 나눠 쓴다)
- 서버: network 스레드 5 + game 스레드 5, 존 1개, 틱 50ms, JobSerializer 시간 예산 64ms
- 봇: 스레드 4. 0.5~2초마다 8방향 이동 또는 정지(정지 확률 1/9), 움직이는 동안 250ms마다 `C_Move` 재전송(클라 `SelectedPlayer.cs`와 같다)
- 재현: `scripts/loadtest.sh` (봇 수마다 30초. 5초 구간 6개 중 접속 구간인 첫 구간을 빼고 나머지 5구간의 범위를 적었다)

**결과**

|---|---|---|---|---|---|---|---|---|
| 50 | 13.7~14.8 | 15.9~16.5 | 0 | 20 | 43.8k~46.3k | 43.8k~46.3k | 38.0~40.6 | 57~65% |

- CPU 100% = 코어 1개. 세션당 수신(봇 입력)은 세 경우 모두 약 77B/s다.
- 틱 시간은 봇 50→100에서 약 3.8배, 100→200에서 약 4.1배로 늘었다.
- 송신 패킷 수와 async_write 횟수가 거의 같다. 패킷이 묶이지 않고 하나씩 써진다.
- 100명부터 틱이 50ms를 넘어 데드라인을 절반쯤 놓치고, 200명에서는 초당 약 4틱만 돈다. 200명의 세션당 송신이 100명보다 적은 것은 틱이 덜 돌아서다.

**프로파일** (봇 100, `sample`로 4초, Release)
- `World::Tick` 샘플 804개 중 `Session::Write`가 782개(97%)
  - `__sendmsg`(쓰기 시스템 콜) 434개(54%): `async_write`가 시작한 스레드(game 스레드)에서 바로 쓴다
  - `pthread_cond_signal` 231개(29%): 쓰기 완료를 처리할 network 스레드를 깨운다
  - 나머지: 핸들러 메모리 할당 45개, mutex 대기 41개

**측정 중 발견**
- 봇 200이 한꺼번에 끊길 때 서버가 SIGSEGV로 죽었다. `World::MulticastMove`가 이미 만료된 세션(`GetSession()`이 null)에 `Send`를 불렀다(1-5의 "세션 weak_ptr 만료 미확인"). 지표 구간은 그 전에 끝나서 위 수치에는 영향이 없다.

**아직 하지 않은 것**
- 시간 예산 1/5/10/64ms 비교(1-11)

## 1-4 세션 strand 전후

**환경**: 1-11과 같다(Apple M4 Pro, Release, 서버 network 스레드 5 + game 스레드 5, 존 1개, 틱 50ms, 시간 예산 64ms, 봇 스레드 4).
- 부하: `scripts/loadtest.sh` (봇 수마다 30초. 첫 5초 구간을 빼고 나머지 5구간의 범위)
- 경쟁: `scripts/churntest.sh` (TSan 서버 90초, 움직이는 봇 50(DummyClient) + 접속/종료 반복 봇 50(ChurnClient). 반복 봇은 입장한 뒤 봇이 닫기, 잘못된 패킷 보내기, 읽기 멈추기(송신 큐 오버플로)로 3분의 1씩 끊는다)

| 봇 | 틱 p50 (ms) | 틱 p99 (ms) | 데드라인 초과 (5초당) | 송신 패킷 (초당) | async_write (초당) | 쓰기 1번당 패킷 | 세션당 송신 (KB/s) | 서버 CPU |
|---|---|---|---|---|---|---|---|---|

| 100 | 53.1~55.8 | 55.9~62.1 | 49~50 | 88.9k~93.6k | 88.9k~91.1k | 1.00~1.05 | 38.6~40.6 | 126~132% |
| 200 | 220~226 | 227~239 | 80~84 | 144.3k~149.1k | 144.3k~149.1k | 1.00~1.01 | 31.3~32.4 | 206~214% |

- strand 대기시간은 strand가 없어서 비어 있다.

**TSan + 반복 봇** (90초)
- 반복 봇: 봇이 닫기 873회, 잘못된 패킷으로 서버가 끊기 861회, 오버플로로 서버가 끊기 32회(STALL 16자리 × 2회, 전부 끊김 확인)
- TSan 경고 28건

| 분류 | 건수 | 내용 |
|---|---|---|
| 소켓 close ↔ 쓰기 시작 | 9 | network 스레드의 `Disconnect` → `close()`(`Session.cpp:37`, 읽기 에러·핸들러 false에서)와 game 스레드의 `World::MulticastMove` → `Send` → `Write` → `async_write` 시작(`Session.cpp:169`). asio 쪽 위치는 `async_send`, `cleanup_descriptor_data`, close 안의 `construct` |
| `std::cout` | 18 | `Session.cpp:50`(Disconnect), `:60`(HandleError)의 로그를 여러 스레드가 동시에 쓴다(libc++ `ios_base::width`) |
| asio reactor 내부 | 1 | `kqueue_reactor::run`이 descriptor_state의 mutex를 읽는 것과, accept가 새 소켓의 descriptor_state를 만드는 것. 포인터가 커널(kevent)을 거쳐 넘어가서 TSan이 순서를 보지 못하는 것일 수 있다(추정. strand 적용 뒤에도 남는지 본다) |

**크래시** (봇을 다듬으며 TSan 서버로 3번, Release 서버로 1번 돌렸다)
- TSan 60초 1번: game 스레드의 쓰기 시작이 `kqueue_reactor::start_op`에서 SEGV. 바로 앞 경고가 같은 descriptor_state를 network 스레드의 close(`cleanup_descriptor_data`)가 해제한 것이다. 1-4가 고칠 크래시다.
- TSan 90초 1번: 봇이 입장 중에 끊자 `GameSession::OnDisconnected`(`GameSession.cpp:23`)가 아직 없는 World에 `LeavePlayer`를 불러 시작 몇 초 만에 SEGV. 1-5의 "OnDisconnected에서 world가 null"이다. 이 때문에 반복 봇은 입장한 뒤에만 끊게 바꿨다.
- TSan 90초(입장 뒤에만 끊기) 1번과 Release 90초(끊는 방법을 매번 무작위로 고르던 봇) 1번은 크래시 없이 끝났다. 1-4 크래시는 확률적이라 경고 수로 판정한다.

### 후 (2026-10-20, 세션 strand 적용)

**부하**

| 봇 | 틱 p50 (ms) | 틱 p99 (ms) | 데드라인 초과 (5초당) | 실제 틱 (초당) | 송신 패킷 (초당) | async_write (초당) | 쓰기 1번당 패킷 | 세션당 송신 (KB/s) | strand 대기 p50 / p99 (µs) | 서버 CPU |
|---|---|---|---|---|---|---|---|---|---|---|
| 50 | 0.32~0.34 | 0.80~1.40 | 0 | 20 | 43.8k~46.2k | 1.75k~2.07k | 22~25 | 38.0~40.9 | 124~179 / 739~1121 | 4.3~4.8% |
| 100 | 1.27~1.39 | 3.08~4.27 | 0 | 20 | 173.9k~181.8k | 5.93k~6.35k | 28~30 | 75.7~79.6 | 195~271 / 1287~1979 | 12.4~13.5% |
| 200 | 4.0~4.2 | 7.3~37.1 | 0 | 20 | 712k~738k | 19.0k~25.2k | 28~38 | 155.4~161.2 | 122~292 / 1635~3296 | 58.7~69.2% |

- 틱 p50이 봇 50에서 14.8~15.9 → 0.32~0.34ms, 봇 200에서 220~226 → 4.0~4.2ms로 줄었다. 100명부터 놓치던 데드라인이 200명까지 0이고, 틱이 초당 20번 다 돈다.
- 쓰기 1번당 패킷이 1.00~1.05 → 22~38이 됐다. `Send`가 push와 (배치당) post만 하게 되면서, game 스레드가 한 틱의 송신을 strand 대기(p50 약 0.1~0.3ms) 안에 다 넣는다. 그래서 network 스레드가 `Write`를 실행할 때 그 틱에 쌓인 패킷을 한 번에 가져간다. strand가 의도한 배칭은 아니고, strand 대기와 `Send` 속도의 차이에서 생긴 결과다(ADR-008 트레이드오프).
- 같은 일을 하는 봇 50의 CPU가 65~74% → 4.3~4.8%로 줄었다. 1-11 프로파일에서 틱의 97%였던 `Session::Write`(game 스레드의 `sendmsg` 54%, network 스레드 깨우기 29%)가 패킷마다 일어나다가 배치마다 일어나게 됐다.
- 바이트는 그대로 N²이다. 봇 200의 세션당 송신은 155~161KB/s(전체 약 31MB/s)이고, 전에는 틱이 초당 4번만 돌아서 31~32KB/s로 보였을 뿐이다. AOI(R4)가 줄일 것은 이 바이트다.
- 봇 200의 틱 p99가 구간에 따라 7~37ms로 흔들린다. 원인은 아직 보지 않았다.

**TSan + 반복 봇** (`scripts/churntest.sh`, 120초)
- 반복 봇: 봇이 닫기 1157회, 잘못된 패킷으로 서버가 끊기 1164회, 오버플로로 서버가 끊기 16회(STALL 16자리 전부)
- TSan 경고 0건. 서버 크래시 없음
- Release 서버 120초: 봇이 닫기 1198회, 잘못된 패킷 1172회, 오버플로 16회, 크래시 없음
- STALL 대기를 40초 → 60초, 기본 실행 시간을 90초 → 120초로 늘렸다. strand 적용 뒤 TSan 서버(봇 50 + 50)에서는 STALL 세션의 커널 송신 큐(약 147KB)가 차는 데만 20초 넘게 걸려, 40초 대기로는 서버 큐(320KB)가 넘치기 전에 확인하게 되어 오버플로 경로가 검사되지 않았다(2번 연속 0/16). 봇 3개 TSan, Release에서는 40초로도 끊겼다.
- "전"에 1건 나오던 asio reactor 내부 경고(`kqueue_reactor::run`이 `conditionally_enabled_mutex::enabled_`를 락 없이 읽음)는 이번 120초 실행에서는 나오지 않았고, strand 적용 뒤 봇 3개 실행에서는 1건 나왔다. asio 소스(`kqueue_reactor.ipp:494`)를 보면 accept 스레드가 만든 descriptor_state를 network 스레드가 kevent가 돌려준 포인터로 읽고, 둘 사이의 순서는 커널만 보장한다. TSan이 볼 수 없는 순서라 오탐으로 본다.
