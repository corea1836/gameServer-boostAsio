이 프로젝트는 Harness 프레임워크를 사용한다. 아래 워크플로우에 따라 작업을 진행하라.

---

## 워크플로우

### A. 탐색

`/docs/` 하위 문서(PRD, ARCHITECTURE, ADR)를 읽고 프로젝트의 기획·아키텍처·설계 의도를 파악한다. 필요시 Explore 에이전트를 병렬로 사용한다.

### B. 논의

구현을 위해 구체화하거나 기술적으로 결정해야 할 사항이 있으면 사용자에게 제시하고 논의한다. 새 단계(AOI, 몬스터, 스킬 등)는 grilling으로 설계를 정하고, 결정은 `docs/ADR.md`에 기록한다.

### C. 작업 설계

사용자가 구현 계획 작성을 지시하면 여러 작업으로 나뉜 초안을 작성해 피드백을 요청한다.

설계 원칙:

1. **Scope 최소화** — 하나의 작업에서 하나의 레이어 또는 모듈만 다룬다. 여러 모듈을 동시에 수정해야 하면 작업을 쪼갠다.
2. **담당 명시** — 학습 대상 파트는 담당을 "사용자" 또는 "Claude 테스트 → 사용자"로 적는다. Claude는 이 작업을 구현하지 않는다(CLAUDE.md CRITICAL).
3. **근거 위치 명시** — 관련 코드 위치(`파일:줄`)와 문서 섹션(ADR 번호 등)을 적는다. 작업자가 코드를 읽고 맥락을 파악한 뒤 작업하도록 유도한다.
4. **시그니처 수준 지시** — 함수/클래스의 인터페이스만 제시하고 내부 구현은 작업자 재량에 맡긴다. 단, 설계 의도에서 벗어나면 안 되는 핵심 규칙(스레드 소유권, 데이터 무결성 등)은 반드시 명시한다.
5. **검증은 로직 종류에 맞춘다** (ADR-016) — "~가 동작해야 한다" 같은 추상적 서술 대신 확인할 수 있는 기준을 적는다.
   - 규칙 로직: 실행 가능한 테스트 커맨드 (`cmake --build build && ctest --test-dir build`)와 테스트 케이스 목록
   - 감각·튜닝 로직: 지킬 불변식 + 플레이로 확인할 항목
   - 동시성·네트워크: 봇 시나리오 + TSan 경고 0건
   - 실험: `docs/measurements.md`에 남길 측정 항목
6. **주의사항은 구체적으로** — "조심해라" 대신 "X를 하지 마라. 이유: Y" 형식으로 적는다.

### D. 반영과 진행

사용자가 승인하면 `docs/PRD.md`의 작업 표에 반영한다(번호, 담당, 상태, 작업, 검증). 작업은 대화에서 하나씩 진행하고, 끝나면 작업 표의 상태를 갱신한다. 측정값은 `docs/measurements.md`에 기록한다.
